# Snippet casing follows merged context via a central, idempotent case-fix pass

Snippets are cut from arbitrary positions in their sources and glued into new contexts in the preview document, so the casing they arrive with is regularly wrong for the merge: a chip beginning lowercase can land at a sentence start, and a sentence-started chip can land mid-sentence. We decided snippet casing follows the merged context: a pure case-fix pass in the preview document utils recomputes the whole document — classifying each snippet token by its predecessor (document start; after sentence-ending `.`, `!`, `?`, or `…`, ignoring trailing whitespace and closing quotes/brackets; after a line break; mid-sentence; or glued to non-whitespace text, which is left alone) — and transforms only the first letter of the first word: capitalized at sentence starts, lowercased mid-sentence. Guards skip all-caps first words including single letters — except first words the rule set's `allCapsExceptions` list exempts (today both language sets exempt the exact word "I", which follows the general rules) — mixed-case first words (brands like "iPhone"), non-letter first characters, empty tokens, and user-edited ("frozen") tokens. The pass is wired centrally in the snippetsReducer wrapper after every transition except SYNC_DOCUMENT (so it always sees canonical shapes after reconciliation's source-text rewrite and eager normalization, and so corrections never fight the focused editor mid-typing), and on the copy path, where it applies to a transformed copy of the tokens before serialization: the clipboard is always fully corrected while the document is corrected only at triggers. There is no source-context guard: the pass never consults how the text was cased in its source — proper names cut from mid-sentence sources can be lowercased mid-merge; wrong corrections are fixed by hand, and a deferred undo task exists as roadmap Feature 4 Task 3. Rule sets are keyed by the active UI language — carried in the snippets store's state (the provider dispatches on i18n's `languageChanged`, so a runtime switch re-derives the document and the copy payload under the new language) — identical content for en-US and pt-BR today. The comparison policy is mixed: reconciliation's no-op guard is case-aware (case-only re-emissions produce reference-identical state), while the edited-detection comparison in SYNC_DOCUMENT and the focused surface's self-recognition comparison stay exact — a case-only retyping freezes the chip as a user edit (manual overrides are final), and a pass-induced model change is never mistaken for the surface's own typing.

## Considered Options

- **Per-trigger wiring at each call site (creation, sort, copy)** — three call sites drift; the moved chip's neighbors (whose predecessors changed) are easy to miss; the wrapper is one seam and the whole-document recompute makes coverage structural.
- **Remembering the source's original casing per token (roadmap Task 1.1's "capitals that were already mid-sentence in the source" guard)** — dropped by user decision 2026-10-22: corrections apply purely from merged context; the user prefers hand-fixing wrong corrections to source-tracking complexity.
- **A standalone "I" guard (roadmap Task 1.1's original list)** — dropped by user decision 2026-10-22: "I" follows the general contextual rules (mid-sentence "I" → "i" — wrong by English orthography, accepted and fixed by hand); with it gone, the en-US and pt-BR rule sets are identical.
- **Running the pass on SYNC_DOCUMENT too** — rejected: corrections would rewrite the focused surface between keystrokes, fighting the editor (ADR 0004); the copy path already guarantees a fully corrected clipboard for the stale window.
- **All comparisons exact** — every case-only source re-emission would flip corrected tokens back to source case and re-correct them: reference-unstable churn and needless focused-surface remounts.
- **All comparisons case-tolerant** — a deliberate case retyping would no longer freeze the chip (manual overrides would never stick) and corrections would be mistaken for the editor's own typing (false freezes).
- **A central pass in the reducer wrapper (skip SYNC_DOCUMENT) + the copy-path copy — chosen.**

## Consequences

- Triggers: every reducer transition except SYNC_DOCUMENT (creation via SET_SOURCE_SNIPPETS; sorts via MOVE_TOKEN / MOVE_TOKEN_TO_LANDING) plus the copy path; copy never mutates the document.
- Frozen chips are never re-corrected — hand edits are final (roadmap Task 1.4's "manual override survives" test); the accepted side effect: text typed later into an edited chip is never auto-corrected either.
- The visible document can hold stale casing after typing until the next trigger; the clipboard is always fully corrected.
- A pass-induced model change while edit is ON and the surface is focused is a non-text change: the focused surface re-freezes/re-renders and the caret may reset (the accepted ADR 0004 trade-off).
- Proper names get lowercased mid-merge ("Paris" → "paris") and mid-sentence "I" becomes "i" — both wrong-by-orthography outputs are accepted; users fix them by hand; a deferred undo task is recorded as roadmap Feature 4 Task 3.
- Roadmap Task 1.1's guard list is amended at completion: "standalone 'I'" and "capitals that were already mid-sentence in the source" are dropped (user decisions 2026-10-22); Task 1.2's case-aware-comparison wording resolves to the mixed policy (reconcile no-op case-aware; edited-detection and focused-surface comparisons exact).
- Rule sets are keyed by the UI language, which rides in the store state and is kept current by the provider's `languageChanged` dispatch (the reducer is a pure (state, action) function; display and clipboard always derive under one rule set) — a structural extension point awaiting a content-language mechanism (the per-input picker idea is deferred).
- Abbreviations are not handled: a period always classifies a sentence end ("Dr." capitalizes the next chip).
