```ts
// PreviewArea.hook.tsx — the mode-aware focused-surface-owns-DOM contract (ADR 0004)
// Own parsed edits: parse → ONE whole-document sync; the parse is kept
// for classification (a NO-OP sync re-renders nothing, so a one-shot
// flag would stick and wrongly absorb the next external change).
const dispatchParsedSync = useCallback((parsed: PreviewToken[]) => {
  lastParseRef.current = parsed;
  syncDocument(parsed);
}, [syncDocument]);

// The document-change effect classifies every incoming change against
// the last dispatched parse — content-equal ignoring `edited` (the
// reducer's only transform) means it is this surface's own parsed
// edit: absorb (the frozen children stay). Every other change (a
// completed drag, source reconciliation) re-freezes the focused
// surface from the model + remounts (clean reconciliation, accepted
// caret reset).
useEffect(() => {
  const ownParse = lastParseRef.current;
  lastParseRef.current = null;   // classified: a stale parse must never absorb a later change
  if (ownParse !== null && tokensEqualIgnoringEdited(previewDocument, ownParse)) {
    modelRef.current = previewDocument;
    return;
  }
  if (previewDocument !== modelRef.current) {
    modelRef.current = previewDocument;
    if (editEnabled && flowFocused) { setFrozenTokens(previewDocument); setRenderEpoch((e) => e + 1); }
  }
}, [previewDocument, editEnabled, flowFocused]);

// Blur (and toggling edit OFF mid-typing) commits first — no keystroke lost.
const handleFlowBlur = useCallback((event) => {
  if (event.target !== flowRef.current) return;   // chip blur must not thaw
  commitFlow();
  setFlowFocused(false); setFrozenTokens(null); setRenderEpoch((e) => e + 1);
}, [commitFlow]);
```

- **Document model (3.1)**: SnippetsContext state is `{ tokens, tombstones, editEnabled }`; `tokens` is a single ordered `PreviewToken[]` where position IS the merge order. Snippet tokens carry `tokenId` (`${sourceId}:${sourceSnippetId}` — globally unique, the sortable id), `sourceSnippetId`, `sourceId`, `color`, `text`, `edited`; own-text tokens never contain `\n`; line-break tokens serialize `\n`. `useSnippets` exposes `document`, `editEnabled`, `setSourceSnippets`, `moveToken(from, to)`, `syncDocument(tokens)`, `setEditEnabled` — all stable references.
- **Reconciliation**: an emission into an empty document yields `[A, " ", B]`; later appends each insert one `" "` separator first (join parity — an unedited session serializes byte-identically to the old `join(' ')`); resizes rewrite unedited tokens in place (position/color/identity unchanged); edited tokens are text-frozen but still removed when the source deletes them (with one adjacent `" "` separator — preceding when present, else the following one — so an unedited flow keeps join parity through deletions too); tombstoned ids never re-append while the source still reports them, clear once it stops, and never block new ids (TextInput `generateId`).
- **Editable surface (3.2)**: edit OFF renders exactly today's read-only flow (no `contenteditable` attribute, React reconciles freely); edit ON makes the `preview-segment-flow` root the editing host (implicit textbox role, `aria-multiline`, translated `editing.label`, `data-placeholder` hint, text cursor, one-line min-height). Own text renders as plain text nodes, line breaks as `\n` text nodes (the flow's `white-space: pre-wrap` carries them), chips keep their tint/testids/dnd-kit wiring and gain `data-token-id`.
- **Focused-surface contract**: while focused, the surface's own input events parse the DOM and dispatch one `SYNC_DOCUMENT` — the children memo (`renderedTokens`) does not recompute (React bails on identical element references; the browser-created text node stays the same node — asserted by node identity). Blur commits, thaws and remounts from the model; non-text changes (completed drag, source reconciliation) re-freeze + remount the focused surface; toggling edit OFF mid-typing commits the DOM first.
- **Chip territory and arrow scaffolds (round 5, user decision 2026-10-18).** **Rule A — the redirect.** EVERY input event still syncs the model (EDIT-33 sacred; the redirect gates gate only the redirect). A non-whitespace `insertText` at a caret position that DIRECTLY abutted a chip (the boundary walk crosses exactly the typed run to a left chip, or nothing to a right chip — `chipBoundaryFromCaret` returns the crossed text) is the chip's TERRITORY: the typed run is removed from the flow and re-inserted INTO the chip (append after its text for a left chip, prepend before it for a right chip), and the caret follows inside the chip (subsequent typing integrates natively, Q3; the chip's `edited` flag becomes true). If the insertion point's far side directly abuts non-whitespace own text (e.g. `mytext|` before a chip), ONE space is planted outside the chip between them (the >=1-space rule holds: `mytext Xbeta`). A line break between the caret and a chip separates that side (free territory), but a chip directly abutting the caret on the other side still redirects (`\n|chip` redirects into the chip's start). The SEAM — two glued chips with the caret exactly between — keeps the round-4 behavior (agent default: spaces both sides, own text). Whitespace typing, deletions, bare (data-less) events, and non-abutting positions never redirect; Enter (round 2) and paste (round 3) are untouched (no input event on their manual paths — the round-3 at-end paste split composes unchanged).  **Rule 2 — gap collapse.** A spaces-only (no `\n`) run DIRECTLY between two chips is "the gap": while the caret stays inside it, any number of spaces remains; the moment the caret leaves it (selectionchange-driven click/arrows, blur — and toggling edit off), a >1-space gap collapses to exactly one space (the first text node keeps `" "`, the rest are emptied — the parser prunes them) and one commit resyncs the model, so the blurred twin re-renders. Never collapse: runs containing `\n`, runs not bounded by chips on both sides, single-space gaps, and never while the caret is inside. Both rules go through the same own-parse sync — no epoch bumps, the caret survives.
- **Enter**: preventDefault'd (no native block insertion). **"A line break never enters a snippet" (user decision 2026-10-17):** browsers place a click-at-the-end caret INSIDE the chip's text node, so the handler first classifies the caret relative to the nearest `[data-token-id]` ancestor — a collapsed caret at a chip's END text boundary inserts the `"\n"` as a SIBLING immediately after the chip element (start boundary: immediately before it), the caret follows the newline, and text typed on the new line is own text in the flow, never snippet content; the chip's token text is unchanged (its reconciliation tracking is untouched too — no edited flag). Every other caret (mid-chip, outside any chip, non-collapsed selections) keeps the `insertTextAtSelection('\n')` path — a mid-chip Enter still embeds the newline into the chip (Q3 integration; splitting stays the rejected deviation b), and typing a regular character at a chip's end still integrates it into the chip. After either path, the **bogus `<br>` line anchor** is planted when the newline now ends the block (Chrome's own pre-wrap contentEditable technique — a trailing `"\n"` renders no empty last line; the anchor forces the line box and the caret — left between the two — renders on the new line), then an explicit commit runs (manual DOM edits fire no input event). The anchor never stacks (an existing one is enough), is planted only when nothing meaningful follows the newline, never touches the selection (so the re-focus path reuses it without moving a user-placed caret), is parser/serialization-neutral (`<br>` has no textContent → no token; the WYSIWYG invariant holds even while focused), self-heals away on every thaw re-render, and is not a droppable/sortable node so dnd-kit's rects are unperturbed. The same anchor rule applies on re-focus (a document that already ends with a line-break token gets the anchor planted so clicking at the end shows the caret on the empty line) and on paste ending with `"\n"`. The Enter handler is guarded by `event.target === flowRef.current` so Space/Enter on a focused chip stays dnd-kit's pickup (verified: the activator preventDefaults and only activates on its own node).
- **Parsing/sync (3.4)**: `parsePreviewDom` is pure — chips → snippet tokens (typed-inside text integrates into the token, deviation b; emptied chips pruned; duplicate ids degrade to text), text nodes split at every `\n`, unknown elements (gap anchors, needle, stray wrappers) are transparent containers that flatten to their text content. Paste is intercepted: `text/plain` only, multi-line preserved, no text data → no-op — and the same "a line break never enters a snippet" rule as Enter (user decision 2026-10-17, round 3): pasted text integrates into the chip only up to its first newline. At the chip's END boundary the paste splits — the prefix inserts at the caret inside the chip (integration; the chip's `edited` flag becomes true), the first newline and everything after land as flow content immediately after the chip; an empty prefix (the paste starts with `\n`) reduces to the Enter escape. At the chip's START boundary the WHOLE paste lands before the chip (a geometric agent default: integrating the prefix would scramble the pasted reading order — only the chip's text follows the caret there, so the tail would render before the prefix without splitting the chip, the rejected deviation b — so the whole paste stays flow content, order preserved, chip text and `edited` untouched). Mid-chip multi-line pastes and single-line pastes everywhere keep the full-integration path (single-line pastes behave exactly like typed characters; an order-preserving escape at mid-chip is impossible without splitting). Every paste path runs the same round-1 trailing-`\n` anchor bookkeeping and the same commit; the WYSIWYG invariant holds on every path.
- **Serialization (3.5)**: `serialize(document)` is pure concatenation; `CopyMergedTextButton` and the modal trigger gate on `editEnabled || serialize(document).length > 0`; copy on an empty document (edit ON) writes `""` and shows the existing toast; own-text-only documents copy.

## 3. Key implementation decisions (agent defaults, within spec latitude)

- **MOVE separator hygiene.** A literal single-element splice cannot preserve the pinned parity (`EDIT-05`: "WYSIWYG parity with the pre-migration snippets array", and the Q16 policy keeping the existing reorder-behavior assertions green): splicing `[a, " ", b, " ", c]` naively yields a leading/dangling separator and `" b ac"`-style serializations. The reducer therefore moves the chip together with ONE adjacent `" "` separator (the same adjacency rule source deletion uses) and re-inserts **the actual carried token object** — id and identity preserved — on whichever side of the landing point lacks one: left-side separator covers → plant after the chip; no left separator with content before → plant before it; document start with content following → after it. The carried token is **never minted and never dropped**: ids stay unique across any sequence of moves (no `:moved-separator` minting), the document's character multiset survives every move in edited documents too, and React keys stay stable across moves. Every canonical case was hand-verified against the old `join(' ')` (forward/backward chip drops, leading/middle/trailing gaps, own-gap no-ops) and is now machine-verified by the exhaustive oracle and the randomized fuzz (§4). No renumbering, no-op guards, and inert moves returning the reference-identical state are unchanged.
- **Any `" "` text token is a movable separator (documented agent default, tester finding 6).** The model deliberately does not distinguish user-typed single spaces from reconciliation-planted separators: `isSeparatorToken` is content-based (`kind === 'text' && text === ' '`). Consequence: a chip drag can RELOCATE a user-typed single space (e.g. dragging a chip whose adjacent user space travels with it) — content is always preserved, never created or destroyed. Spaces with any other shape (multi-space runs, `"hi "`) are ordinary own text and never travel.
- **The freeze mechanism is a children memo over a frozen snapshot.** `renderedTokens = frozenTokens ?? document`: on focus the snapshot freezes at the current model; the surface's own syncs never touch it (memo stable → React bails on identical element references → the DOM is never reconciled mid-typing); non-text model changes re-freeze to the new model; blur/toggle-off commit then null it (thaw). `renderEpoch` keys the flow root so every thaw is a clean remount — React's reconciliation never runs against browser-managed DOM, and the remount is also what resets the native undo stack (the documented limitation). **Self-edit classification drains by document comparison** (tester cycle-1 fix): a NO-OP sync (the reducer returns reference-identical state) produces no re-render, so a one-shot flag would stick and wrongly absorb the NEXT external change; the effect instead classifies every incoming document against the last dispatched parse via `tokensEqualIgnoringEdited` (the reducer's only transform on a parse is the `edited` flag), and a consumed or stale parse never classifies a later change.
- **`document` is aliased on destructure in every hook** (`const { document: previewDocument } = useSnippets()`): the context value's key stays `document` (pinned by the spec), but the DOM global must stay reachable — the modal's Escape guard re-dispatches through `window.document.dispatchEvent`, and shadowing it was a real crash found during implementation.
- **The parser is fully DOM-pure; the reducer owns model semantics.** `parsePreviewDom` takes only the root and the previous tokens (metadata inheritance for color/source ids); the `edited` flag and tombstone writes are computed in `SYNC_DOCUMENT` (text changed vs the previous model token with the same id; never resets; source-side updates never set it). Id spaces are disjoint by prefix (`own-text:`, `line-break:`, `:separator`), so React keys stay unique.
- **The trailing gap anchor renders only while at least one chip exists** — otherwise the flow would never match `:empty` and the placeholder could never show. The spec's flagged caveat (stray zero-length text nodes while focused) remains; the absolutely-positioned overlay is the documented fallback.
- **Test infrastructure — fake-timer drain.** dnd-kit's sensor removes its document-level click-suppression listener (capture-phase `stopPropagation`, attached once the activation constraint is met) via `setTimeout(…, 50)` on drag end. Under `vi.useFakeTimers()`, `vi.useRealTimers()` in `afterEach` discarded that pending removal, and **every subsequent `fireEvent.click` in the file was silently swallowed** (diagnosed with a minimal probe: even a plain `useState` button's onClick stopped firing). The two pre-existing fake-timer pointer suites (and the new one) now drain 60ms of fake clock before restoring real timers. Zero assertions changed; without it, any later click-driven test in these files would pass or fail vacuously.
- **Two scoped lint suppressions** (`react/set-state-in-effect` in PreviewArea.hook) for the effects that synchronize with the external shared-document/edit-toggle changes — the rule's own sanctioned use case; verified that oxlint honors `eslint-disable-next-line`.
- **Gating helper**: `isDocumentEmpty` is computed once in the hook (`serialize(document).length > 0`) and shared by the copy gate and the empty-state branch; the modal-open trigger re-derives the same expression in `PreviewModal.hook` (one gate semantics, two call sites — both `editEnabled || serialize(document).length > 0`).
- **The i18n keys are consumed through the hook** (`editingLabel`/`editingPlaceholder`) rather than re-read in JSX, keeping the component slim and the language-switch test at the hook boundary.

## 6. Deviations from spec.md

No requirement's contract deviated except two post-delivery clauses, both user decisions (2026-10-17). The two roadmap deviations (a) and (b) are user decisions (2026-10-16) that the spec itself bakes in verbatim (EDIT-20/26 and EDIT-34 record them); both roadmap lines are updated at completion exactly as the spec prescribes. The judgment calls inside the spec's latitude:

- **Post-delivery adjustments (2026-10-17) — user-reported issues and decisions.** (1) **Modal rail order (user decision, user-edited code preserved):** the user moved the edit toggle BELOW the close button in `PreviewModal.tsx` — the modal's tools rail is now copy → close → toggle, superseding the F2/spec rail order "copy → toggle → close" (EDIT-22's rail clause is therefore Deviated; the page toolbar order copy → modal-open → toggle is unchanged; the modal rail-order test was updated, the stale docstrings in `PreviewModal.tsx`/`PreviewModal.styles.ts` were refreshed to record the decision). (2) **Editing-host focus outline removed (user decision):** `outline: none` inside `SegmentFlow`'s `$editing` block only — the caret is a text surface's own focus indicator; the UA's black click-focus box is gone while chips, buttons, and every other focus ring are untouched. (3) **Invisible-last-line caret fix:** Enter at the end of the text created the new line but the caret rendered stuck on the previous line — in `white-space: pre-wrap` a trailing `"\n"` produces no rendered empty last line, so the caret placed after it has no line box. Shipped mechanism: Chrome's own native contentEditable technique — `ensureTrailingLineAnchor` plants a bogus `<br>` right after the trailing newline (never stacked, only when nothing meaningful follows, selection untouched); the anchor is parser/serialization-neutral (`<br>` has no textContent → no token; the WYSIWYG invariant holds even while focused), self-heals away on every thaw re-render, is not a droppable/sortable node, and the same rule covers re-focus (the focus handler plants it when the re-rendered document ends with a line break, so clicking back at the end shows the caret on the empty line) and paste ending with `"\n"`. The CSS `::after` pseudo-newline alternative was rejected in favor of the native technique (the brief's primary); jsdom pins the contracts, the visual result is a manual dev-server item (§7). (4) **"A line break never enters a snippet" (user decision, round 2):** clicking right at the end of a snippet's text places the caret INSIDE the chip span (browsers prefer the innermost text node), so a plain insert made the newline — and everything typed on the next line — part of the snippet token. `classifyCaretRelativeChip` classifies a collapsed caret against the nearest `[data-token-id]` ancestor via exact text-boundary probes; the end boundary (the reported case) and the start boundary (symmetric completion — agent default) take the `insertLineBreakOutsideChip` escape (the `\n` planted as the chip's sibling, the caret after it); mid-chip Enters, typed characters at a chip's end, and non-collapsed selection-Enters all keep the Q3 integration path (the boundary predicates are pinned as exact — a chip's trailing space keeps the caret "mid" until it moves past it). The chip's token text — and its `edited` tracking — are untouched by an escape. EDIT-34 is therefore Deviated (refined) per §5. (5) **The paste question is resolved — user decision, round 3:** the same "a line break never enters a snippet" rule applies to pasted text, verbatim: "Pasted text integrates into the snippet only up to its first newline — the first newline and everything after it land outside the chip (line break + own text). Single-line pastes behave exactly like typed characters (integrate)." At the chip's END boundary the paste splits at the first newline (`insertSplitPasteAtChipEnd`: the prefix inserts at the caret inside the chip — Q3 integration, the chip's `edited` flag becomes true — and the tail lands as the chip's following sibling; an empty prefix is the round-2 Enter escape exactly). At the chip's START boundary the WHOLE paste lands before the chip as flow content — a geometric agent default: only the chip's text follows the caret there, so integrating the prefix would scramble the pasted reading order (the tail would render before the prefix) without splitting the chip (the rejected deviation b); the whole-paste path preserves the reading order and leaves the chip text and `edited` flag untouched. Mid-chip multi-line pastes keep full integration (agent default, documented: consistent with mid-chip Enter — an order-preserving escape is impossible without splitting). Every paste path runs the same round-1 trailing-`\n` anchor bookkeeping (a tail ending the block gets the bogus `<br>`; a following separator/chip does not) and the same per-input commit. (6) **White-space rules (user decision, round 4):** the user's cases, verbatim: "we always have at least one white space between snippets and texts.
