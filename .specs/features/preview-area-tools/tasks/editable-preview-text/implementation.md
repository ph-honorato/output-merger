**Implemented:** 2026-10-16

**Status:** Implemented — Feature 3, Task 3 (roadmap 3.1–3.6) complete; verified by 221 new automated tests (415 total across 17 files), oxlint, `tsc -b`, `vite build`. Both roadmap deviations (a: the edit-text toggle replaces the drag on/off toggle; b: typing inside a snippet integrates instead of splitting — user decisions 2026-10-16) are implemented exactly as specified and the roadmap lines 3.3/3.4 are updated. Five post-delivery deviations from the spec's literal contracts — user decisions 2026-10-17 (EDIT-22's rail clause: modal rail now copy → close → toggle; EDIT-34 refined: "a line break never enters a snippet" — typed CHARACTERS integrate, a newline at a chip boundary escapes the chip on both the Enter and the paste paths; EDIT-35 refined: the white-space rules) and 2026-10-18 (EDIT-28 refined: pointer sorting disabled while editing, keyboard sorting live via Ctrl+Space; EDIT-29 refined: chips are plain spans while editing — Ctrl+Space from the caret is the entry; §5/§6). The judgment calls (MOVE separator hygiene, the jsdom caret-typing fallback, a test-infrastructure timer drain in the two pre-existing fake-timer pointer suites) are recorded in §3/§6. **Post-review correction (tester cycle 1, 2026-10-16):** two blocker fixes in `MOVE_TOKEN` (a dropped carried separator in edited documents; minted duplicate `:moved-separator` ids — both eliminated by re-inserting the ACTUAL carried token object), the self-edit classification drained by document comparison instead of a one-shot flag, and the tester's oracle/fuzz harnesses ported as permanent regression tests (§4/§6). **Post-delivery adjustments (2026-10-17):** two user-reported UI fixes (the editing host's UA focus outline removed — the caret is the indicator; the invisible-last-line caret bug fixed with Chrome's bogus-`<br>` anchor technique), the user's "a line break never enters a snippet" rule — round 2 for Enter at a chip's end/start boundary, round 3 extended to pasted text ("pasted text integrates into the snippet only up to its first newline"), round 4's white-space rules — typing auto-separation plus between-chips gap collapse on caret exit — and round 5's caret-model refinement (user decision 2026-10-18): typing at a chip-abutting caret position is the chip's TERRITORY (the run redirects into the snippet), arrows scaffold the free zones (between-chips gaps expand to two spaces; doc edges get a provenance-tracked space that vanishes when untouched), and round 6's sorting-mode split (user decision 2026-10-18): while editing the mouse serves the editor (pointer sorting unmounted, text cursor everywhere, chips plain selectable spans) and keyboard sorting enters via Ctrl+Space at the caret — Enter drops, Escape returns the snippet to its place (§2/§3/§6/§7). **Post-review correction (tester round-4 cycle 1, 2026-10-17):** the round-4 input gates early-returned before the per-input model sync (real-browser deletions and whitespace keystrokes would have lagged the model) — restructured to gate ONLY the separation, with every input event syncing; the realistic-`InputEvent` repro is ported as regressions (§4/§6). **Post-delivery adjustment round 7 (user decision 2026-10-19):** word-boundary landings — "a dragged snippet must be droppable at every word boundary of the document": the landing model (`MOVE_TOKEN_TO_LANDING` token-gap/text-split landings with the ≥1-space-each-side space accounting and the documented no-carry plant exception; the deduped zero-footprint anchor set inside/beside own text; the `dropLanding` needle; the `landingKeyboardCoordinates` reading-order walk through chips AND anchors in both drag modes; the exhaustive string-level oracle — 258 sweep pairs, 110 old-slot parity pairs, 85 delegation pairs — plus the component/modal/getter suites) (§2/§3/§4/§6/§7). **Tester cycle 1 (2026-10-19) PASSED with one fixed finding:** the round-7 parser merge was serialization-preserving, not shape-preserving — fixed by eager reducer normalization (`normalizeTextTokens` over every action result, reference-identity guarded), making the two reproduced merge-history divergences deterministic single behaviors (pinned) (§4/§6). **Dev-server correction (2026-10-19, "The sort by keyboard is not working"):** the round-7 keyboard walk's reading order was geometric (top, left) — scrambled by the real 0x0 anchor geometry (the jsdom mocks shared top 0, masking it); fixed by sorting the walk in DOM document order via the droppable registry's node refs, and the realistic 0x0 anchor geometry is now the DEFAULT in all rect mocks (§2/§4/§6). **Post-delivery adjustment round 8 (user decision 2026-10-19):** "auto position the caret on the last position of the text in preview area when enabling edit text mode" — the OFF→ON toggle focuses the host and places the caret at the text's end (the visible surface wins the focus; content-identical commits no longer ripple sibling-surface remounts) (§2/§4/§6/§7).

  lastParseRef.current = parsed;
  syncDocument(parsed);
}, [syncDocument]);

// The document-change effect classifies every incoming change against
// the last dispatched parse — content-equal ignoring `edited` (the
// reducer's only transform) means it is this surface's own parsed
// edit: absorb (the frozen children stay). Every other change (a
// completed drag, source reconciliation) re-freezes the focused
// surface from the model + remounts (clean reconciliation, accepted
// caret reset).
useEffect(() => {

  if (ownParse !== null && tokensEqualIgnoringEdited(previewDocument, ownParse)) {
    modelRef.current = previewDocument;
    return;

    modelRef.current = previewDocument;

}, [commitFlow]);

- **Document model (3.1)**: SnippetsContext state is `{ tokens, tombstones, editEnabled }`; `tokens` is a single ordered `PreviewToken[]` where position IS the merge order. Snippet tokens carry `tokenId` (`${sourceId}:${sourceSnippetId}` — globally unique, the sortable id), `sourceSnippetId`, `sourceId`, `color`, `text`, `edited`; own-text tokens never contain `\n`; line-break tokens serialize `\n`. `useSnippets` exposes `document`, `editEnabled`, `setSourceSnippets`, `moveToken(from, to)`, `syncDocument(tokens)`, `setEditEnabled` — all stable references.
- **Reconciliation**: an emission into an empty document yields `[A, " ", B]`; later appends each insert one `" "` separator first (join parity — an unedited session serializes byte-identically to the old `join(' ')`); resizes rewrite unedited tokens in place (position/color/identity unchanged); edited tokens are text-frozen but still removed when the source deletes them (with one adjacent `" "` separator — preceding when present, else the following one — so an unedited flow keeps join parity through deletions too); tombstoned ids never re-append while the source still reports them, clear once it stops, and never block new ids (TextInput `generateId`).

## 3. Key implementation decisions (agent defaults, within spec latitude)

- **MOVE separator hygiene.** A literal single-element splice cannot preserve the pinned parity (`EDIT-05`: "WYSIWYG parity with the pre-migration snippets array", and the Q16 policy keeping the existing reorder-behavior assertions green): splicing `[a, " ", b, " ", c]` naively yields a leading/dangling separator and `" b ac"`-style serializations. The reducer therefore moves the chip together with ONE adjacent `" "` separator (the same adjacency rule source deletion uses) and re-inserts **the actual carried token object** — id and identity preserved — on whichever side of the landing point lacks one: left-side separator covers → plant after the chip; no left separator with content before → plant before it; document start with content following → after it. The carried token is **never minted and never dropped**: ids stay unique across any sequence of moves (no `:moved-separator` minting), the document's character multiset survives every move in edited documents too, and React keys stay stable across moves. Every canonical case was hand-verified against the old `join(' ')` (forward/backward chip drops, leading/middle/trailing gaps, own-gap no-ops) and is now machine-verified by the exhaustive oracle and the randomized fuzz (§4). No renumbering, no-op guards, and inert moves returning the reference-identical state are unchanged.
- **Any `" "` text token is a movable separator (documented agent default, tester finding 6).** The model deliberately does not distinguish user-typed single spaces from reconciliation-planted separators: `isSeparatorToken` is content-based (`kind === 'text' && text === ' '`). Consequence: a chip drag can RELOCATE a user-typed single space (e.g. dragging a chip whose adjacent user space travels with it) — content is always preserved, never created or destroyed. Spaces with any other shape (multi-space runs, `"hi "`) are ordinary own text and never travel.
- **The freeze mechanism is a children memo over a frozen snapshot.** `renderedTokens = frozenTokens ?? document`: on focus the snapshot freezes at the current model; the surface's own syncs never touch it (memo stable → React bails on identical element references → the DOM is never reconciled mid-typing); non-text model changes re-freeze to the new model; blur/toggle-off commit then null it (thaw). `renderEpoch` keys the flow root so every thaw is a clean remount — React's reconciliation never runs against browser-managed DOM, and the remount is also what resets the native undo stack (the documented limitation). **Self-edit classification drains by document comparison** (tester cycle-1 fix): a NO-OP sync (the reducer returns reference-identical state) produces no re-render, so a one-shot flag would stick and wrongly absorb the NEXT external change; the effect instead classifies every incoming document against the last dispatched parse via `tokensEqualIgnoringEdited` (the reducer's only transform on a parse is the `edited` flag), and a consumed or stale parse never classifies a later change.
- **`document` is aliased on destructure in every hook** (`const { document: previewDocument } = useSnippets()`): the context value's key stays `document` (pinned by the spec), but the DOM global must stay reachable — the modal's Escape guard re-dispatches through `window.document.dispatchEvent`, and shadowing it was a real crash found during implementation.
- **The parser is fully DOM-pure; the reducer owns model semantics.** `parsePreviewDom` takes only the root and the previous tokens (metadata inheritance for color/source ids); the `edited` flag and tombstone writes are computed in `SYNC_DOCUMENT` (text changed vs the previous model token with the same id; never resets; source-side updates never set it). Id spaces are disjoint by prefix (`own-text:`, `line-break:`, `:separator`), so React keys stay unique.
- **The trailing gap anchor renders only while at least one chip exists** — otherwise the flow would never match `:empty` and the placeholder could never show. The spec's flagged caveat (stray zero-length text nodes while focused) remains; the absolutely-positioned overlay is the documented fallback.
- **Test infrastructure — fake-timer drain.** dnd-kit's sensor removes its document-level click-suppression listener (capture-phase `stopPropagation`, attached once the activation constraint is met) via `setTimeout(…, 50)` on drag end. Under `vi.useFakeTimers()`, `vi.useRealTimers()` in `afterEach` discarded that pending removal, and **every subsequent `fireEvent.click` in the file was silently swallowed** (diagnosed with a minimal probe: even a plain `useState` button's onClick stopped firing). The two pre-existing fake-timer pointer suites (and the new one) now drain 60ms of fake clock before restoring real timers. Zero assertions changed; without it, any later click-driven test in these files would pass or fail vacuously.
- **Two scoped lint suppressions** (`react/set-state-in-effect` in PreviewArea.hook) for the effects that synchronize with the external shared-document/edit-toggle changes — the rule's own sanctioned use case; verified that oxlint honors `eslint-disable-next-line`.
- **Gating helper**: `isDocumentEmpty` is computed once in the hook (`serialize(document).length > 0`) and shared by the copy gate and the empty-state branch; the modal-open trigger re-derives the same expression in `PreviewModal.hook` (one gate semantics, two call sites — both `editEnabled || serialize(document).length > 0`).
- **The i18n keys are consumed through the hook** (`editingLabel`/`editingPlaceholder`) rather than re-read in JSX, keeping the component slim and the language-switch test at the hook boundary.

(3) **Invisible-last-line caret fix:** Enter at the end of the text created the new line but the caret rendered stuck on the previous line — in `white-space: pre-wrap` a trailing `"\n"` produces no rendered empty last line, so the caret placed after it has no line box. Shipped mechanism: Chrome's own native contentEditable technique — `ensureTrailingLineAnchor` plants a bogus `<br>` right after the trailing newline (never stacked, only when nothing meaningful follows, selection untouched); the anchor is parser/serialization-neutral (`<br>` has no textContent → no token; the WYSIWYG invariant holds even while focused), self-heals away on every thaw re-render, is not a droppable/sortable node, and the same rule covers re-focus (the focus handler plants it when the re-rendered document ends with a line break, so clicking back at the end shows the caret on the empty line) and paste ending with `"\n"`. The CSS `::after` pseudo-newline alternative was rejected in favor of the native technique (the brief's primary); jsdom pins the contracts, the visual result is a manual dev-server item (§7). (4) **"A line break never enters a snippet" (user decision, round 2):** clicking right at the end of a snippet's text places the caret INSIDE the chip span (browsers prefer the innermost text node), so a plain insert made the newline — and everything typed on the next line — part of the snippet token. `classifyCaretRelativeChip` classifies a collapsed caret against the nearest `[data-token-id]` ancestor via exact text-boundary probes; the end boundary (the reported case) and the start boundary (symmetric completion — agent default) take the `insertLineBreakOutsideChip` escape (the `\n` planted as the chip's sibling, the caret after it); mid-chip Enters, typed characters at a chip's end, and non-collapsed selection-Enters all keep the Q3 integration path (the boundary predicates are pinned as exact — a chip's trailing space keeps the caret "mid" until it moves past it). The chip's token text — and its `edited` tracking — are untouched by an escape. EDIT-34 is therefore Deviated (refined) per §5. (5) **The paste question is resolved — user decision, round 3:** the same "a line break never enters a snippet" rule applies to pasted text, verbatim: "Pasted text integrates into the snippet only up to its first newline — the first newline and everything after it land outside the chip (line break + own text). Single-line pastes behave exactly like typed characters (integrate)." At the chip's END boundary the paste splits at the first newline (`insertSplitPasteAtChipEnd`: the prefix inserts at the caret inside the chip — Q3 integration, the chip's `edited` flag becomes true — and the tail lands as the chip's following sibling; an empty prefix is the round-2 Enter escape exactly). At the chip's START boundary the WHOLE paste lands before the chip as flow content — a geometric agent default: only the chip's text follows the caret there, so integrating the prefix would scramble the pasted reading order (the tail would render before the prefix) without splitting the chip (the rejected deviation b); the whole-paste path preserves the reading order and leaves the chip text and `edited` flag untouched. Mid-chip multi-line pastes keep full integration (agent default, documented: consistent with mid-chip Enter — an order-preserving escape is impossible without splitting). Every paste path runs the same round-1 trailing-`\n` anchor bookkeeping (a tail ending the block gets the bogus `<br>`; a following separator/chip does not) and the same per-input commit. Implemented as two rules (the White-space rules bullet in section 2): **typing auto-separation** (insertion-type inputs only — deletions never re-add a deliberately deleted separator; typing inside a chip never auto-spaces — Q3; whitespace typing never auto-spaces; own-text-to-own-text glue untouched; the planted spaces leave the caret untouched, inside the typed run) and **gap collapse** (a spaces-only, `

Scope notes: PASTE is out of scope this round (pinned unchanged — the rules are input-event-driven and the paste paths are manual inserts with no input event); the "two white spaces remain" shape arises naturally from rule 1 (typing in the one-space gap plants the missing side, so deleting the text leaves the original space plus the planted one — exactly the user's scenario). The round-4 audit of the existing editing-workflow suites found ZERO glued-typing expectations requiring updates (all near-chip typing in the suites happens inside chips, through newlines, or with leading spaces — Q16: no assertion changed).
